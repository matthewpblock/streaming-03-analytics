# NBA Play-by-Play Streaming Analytics

This site provides documentation for the **NBA Play-by-Play Streaming Analytics** project.

This project demonstrates a real-time data engineering pipeline that uses Kafka to stream NBA events from a producer to a consumer. The consumer reads each event, validates it against a strict data contract, filters the timeline for actual shot attempts, computes live derived analytics (like points scored, shot quality, and clutch status), and enriches the records with player metadata.

Key capabilities demonstrated in this module include:
- **Live Data Extraction:** Utilizing the `nba_api` to fetch game timelines.
- **Strict Data Contracts:** Validating incoming payloads at the producer level to ensure downstream pipeline integrity.
- **Event Filtering:** Ingesting a complete timeline but selectively routing and analyzing specific events.
- **Message-by-Message Analytics:** Calculating advanced basketball metrics on the fly as streaming events arrive.
- **Reference Data Lookup:** Augmenting fast-moving streams with slower-moving reference data (like player and team rosters).

## Custom Project

### Dataset

The project transitioned from a generic e-commerce sales dataset to real-world basketball analytics.
- **Primary Dataset:** `events.csv` (dynamically generated via the `nba_api`).
- **Record Types:** NBA play-by-play events (e.g., shots, rebounds, fouls, timeouts).
- **Fields Included:** `play_id`, `game_id`, `timestamp`, `player_id`, `action_type`, `shot_type`, `distance_ft`, `is_made`, `quarter`, `time_remaining`.
- **Modifications:** The original sales data was entirely replaced. A custom script (`fetch_nba_data.py`) was introduced to fetch live API data and parse play descriptions into structured fields.
- **Reference Dataset:** `players.csv` (contains `player_id`, `player_name`, `team_name`, `position`) used for validation and consumer enrichment.

### Data Contract

To ensure data quality, the pipeline enforces a strict data contract on incoming messages.
- **Required Fields:** `play_id`, `game_id`, `timestamp`, `player_id`, `action_type`, `shot_type`, `distance_ft`, `is_made`.
- **Optional Fields:** `quarter`, `time_remaining`.
- **Allowed Values & References:** `shot_type` must be one of `{"2PT", "3PT", "FT"}`. `player_id` must explicitly exist in the loaded `players.csv` reference table. `distance_ft` cannot be negative.
- **Validity:** A message is valid only if all required fields are present, match expected types, and satisfy the allowed value/reference constraints.

### Kafka Messages

Kafka acts as the real-time event broker for the game stream.
- **Sent Messages:** The producer streams every sequential event from the play-by-play timeline as a JSON payload.
- **Topic Used:** `streaming-03-analytics-nba-pbp`
- **Message Key:** Messages are keyed by `game_id` to ensure that all events for a specific game are routed to the same Kafka partition, preserving chronological order.
- **Changes:** Swapped the generic e-commerce schema for a sports analytics schema. 

### Consumer Validation

The consumer acts as a gatekeeper and filter for the analytics engine.
- **Checks Performed:** Validates against the Data Contract (required fields, bounds, and references). Additionally, it filters the stream by checking the `action_type` field.
- **Acceptance:** If an event is a valid shot attempt (`Made Shot`, `Missed Shot`, `Free Throw`), it passes through to the enrichment and aggregation layers.
- **Rejection/Skipping:** If validation fails, it logs to a rejected CSV. If an event is valid but is a non-scoring play (like a `Rebound` or `Timeout`), it gracefully skips it.
- **Protection:** This layered validation guarantees downstream analytical queries are only calculating metrics on verified, structured shot data rather than unstructured edge-case events.

### Data Engineering and Enrichment

Raw events are enriched into highly valuable business intelligence.
- **Derived Fields:** 
  - `points_scored`: Calculated based on `shot_type` (3, 2, or 1) and whether `is_made` is True.
  - `shot_quality_category`: Categorized logically (e.g., "Paint", "Mid-Range", "NBA Deep 3") based on `distance_ft`.
  - `clutch_shot_flag`: Boolean set to True if the shot occurs in the 4th quarter or Overtime.
- **Reference Data Used:** `players.csv` dictionaries.
- **Transformations:** Replaced regional tax calculation logic with basketball scoring logic. Consumer dynamically joins the fast-moving event stream with the slow-moving `players` lookup to attach readable names and teams.

### Streaming Analytics

As valid shots arrive, the consumer maintains a live scorecard.
- **Summarized Values:** The running statistics target the `points_scored` derived field.
- **Tracked Metrics:** The pipeline logs the `total_pts` (a live scoreboard), `average_pts` per shot attempt, `min_pts` (usually 0 for a miss), and `max_pts` (usually 2 or 3 for a make).
- **Behavior:** As the game progresses, the total score climbs sequentially with each accepted message, mimicking a live TV broadcast graphic.

### Experiments

- **Phase 4 Modification:** Modified `.env` variables to increase `PRODUCER_MESSAGE_COUNT` to 1000 and lower `PRODUCER_MESSAGE_INTERVAL_SECONDS` to 0.1, allowing the pipeline to simulate an entire NBA game rapidly rather than stopping after 20 events.
- **Phase 5 Application:** Transitioned the pipeline out of the standard e-commerce domain and built an entirely new automated data extraction script (`fetch_nba_data.py`) to hit external REST APIs and parse the results into Kafka.

### Results

- **Production:** The producer successfully generated and sent ~490 game events sequentially.
- **Consumption:** The consumer successfully ingested the stream.
- **Accepted vs Skipped:** Around ~100 messages were accepted as valid shot attempts. The remaining ~390 messages (fouls, subs, jump balls) were correctly identified and skipped.
- **Output CSV:** `consumed_events.csv` successfully stored the flattened, enriched shot logs including player names and points scored.
- **Logs:** Terminal outputs vividly showed the game progressing, logging player actions and the rising team scores in real-time.

### Interpretation

This project proved the flexibility and power of streaming architectures.
- **Changes:** Transitioning from e-commerce to sports demonstrated how data contracts are domain-agnostic.
- **Validation Insights:** Learned that robust data contracts prevent bad data (like missing player names on "team rebound" events) from crashing analytical engines.
- **Enrichment Insights:** Learned that separating raw telemetry (IDs, coordinates) from descriptive metadata (names, categories) makes the stream lighter, while the consumer effectively re-combines them for human-readable output.
- **Business Value:** Running summaries offer organizations instant, live situational awareness. In sports broadcasting, this is the exact architecture that feeds live TV graphics and coaches' tablets.
- **Intelligence Gained:** We instantly generated an enriched ledger that makes evaluating player efficiency, shot selection, and clutch performance trivial for data analysts using downstream tools like DuckDB.

### Future Enhancements: Expected Points & Regression Analysis

To push this real-time analytics engine even further, future iterations could track **Expected Points Per Shot (xPPS)** to provide live, actionable insights to coaching staffs during a game.

- **Expected Points Calculation:** By enriching the stream with historical shooting percentages based on `distance_ft`, `shot_type`, and `player_id`, the consumer could calculate an `expected_points` value for every single shot attempt (e.g., a 40% 3-point shooter taking a 3PT shot has an xPPS of 1.2).
- **Real-Time Shot Quality:** By comparing a team's cumulative `expected_points` to their actual `points_scored`, coaches can evaluate the *quality of their shot selection* rather than just looking at the scoreboard. If a team is trailing but generating a high xPPS, the offensive process is working despite missed shots.
- **Regression Toward the Mean:** This live comparison would allow for real-time regression analysis. If a team has scored 25 points on shots that mathematically expect to yield only 15 points, regression suggests their shooting will soon cool down. Conversely, if a team has scored 10 points on an xPPS of 20, analytics suggest their luck will turn and shooting will improve, provided they keep generating the same high-quality looks. This empowers coaches to make adjustments based on underlying process rather than variance-driven results.
